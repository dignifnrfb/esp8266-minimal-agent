# 2026-10-24：TLS 轮询期间看门狗复位的排查与修复

修复版本：`minimal-agent-0.1.5-stack-fix`。基线为
[`0.1.4-breathe-diag` 源码快照](https://github.com/dignifnrfb/esp8266-minimal-agent/tree/256564e7dc47f57a5c4445c0a672cc39db81662b)。
本页记录直接观测、对照实验和本次验收边界；结构化结果见
[verification.json](2026-10-24-tls-stack-overflow.verification.json)。

## 现象与初步隔离

板子在联网轮询时反复重启。115200 波特率串口实际捕获 `Soft WDT reset`，
也观察到硬件看门狗复位。暂停轮询约 72.6 秒时 Wi-Fi 保持连接、启动标识不变；
恢复轮询后约 19.2 秒内再次出现重启，故先把范围缩小到启用轮询后的执行路径。

设备由电脑 USB 直供，无外接电路。用户实际断电至少 10 秒并换线或换 USB 口后，
原固件仍复位。这个对照没有消除故障，单凭它不能测定供电质量。

## 未解决故障的对照

下列候选均未通过实板看门狗验证，未作为修复发布：

- 关闭呼吸灯 PWM。
- 关闭 TLS 会话复用。
- 把超时转发到内部 TLS 上下文并降为 2000ms。
- 调整 TLS 缓冲与控制对象的堆分配。
- 在 TLS 等待循环中使用实际 `delay(1)`。
- 关闭 Wi-Fi 节能。
- 关闭共享 IRAM 第二堆。
- 改用默认 32KiB 缓存 / 32KiB IRAM 布局；该候选约 124 秒后仍复位。

这些结果没有证明所有缓存或硬件因素都不可能参与，但不能把修改缓存布局作为已经验证的修复。

## 直接捕获的栈损坏证据

进一步检查发现，崩溃输出里的 continuation `stack_end` 不再是正常 DRAM 栈地址。
因此添加了仅在本地诊断构建中使用的探针，检查栈边界、保护值和运行控制字段。
在一次 Soft WDT 之前直接捕获以下经过筛选的数值：

| 字段 | 观测值 | 含义 |
| --- | --- | --- |
| 栈大小 | 4096 字节 | 固定 continuation 栈 |
| 最低栈余量 | 48 字节 | 旧版诊断构建的高水位测量 |
| `stack_end` | `0x401035fc` | 已变成代码区地址 |
| 预期 `stack_end` | `0x3fffffd0` | 该次启动的正常边界 |
| `stack_guard1` | `0x3ffede48` | 原应为 `0xfeefeffe`，已被覆盖 |
| `pc_ret` | 被改写 | continuation 返回控制数据受损 |
| `pc_suspend` | 非零 | 在该执行位置不应处于挂起状态 |
| `can_yield()` | 0 | 协作让出不能正常进行，之后触发 WDT |

这里直接确认的是运行栈及其控制数据被破坏。旧版诊断构建的反汇编进一步显示，
编译器把 `receivePoll()` 与 `updateFirmware()` 内联进 `tick()`，使普通空轮询也
预留 OTA 局部变量，`tick()` 栈帧达到 1376 字节。叠加 HTTP/TLS 调用后，4KiB 栈余量不足。
单个 WDT 程序地址只能说明复位时在哪里，不能独自证明最初的覆盖位置。

## 修复

1. 对 `receivePoll()` 和 `updateFirmware()` 使用 `noinline`，隔离普通轮询与任务处理的栈帧。
2. 提取独立且禁止内联的 `streamFirmware()`，避免 OTA 哈希对象和 512 字节下载缓冲
   在 TLS 握手时提前占用调用者栈帧。
3. USB `status` 增加 `stack_ok`、`stack_free`、`reset_reason`，便于后续复核。

最终实际构建的栈帧如下。它们是单个函数的帧大小，不能直接相加作为所有路径的最大栈使用量：

| 函数 | 栈帧字节 |
| --- | ---: |
| `tick()` | 192 |
| `receivePoll()` | 256 |
| `updateFirmware()` | 432 |
| `streamFirmware()` | 800 |

TLS 缓冲仍为 16384/1024 字节，保留 TLS1.2、CA/域名/时间验证和会话复用。
CPU 仍为 160MHz，MMU/共享 IRAM 堆、超时和 PWM 沿用 0.1.4。没有禁用看门狗，
也没有修改全局 PlatformIO 框架文件。

## 验证结果

| 构建 | 连续观察 | 成功轮询 | 额外重启 | 最低栈余量 |
| --- | ---: | ---: | ---: | ---: |
| 仅拆分函数的诊断对照 | 300.14 秒 | 69 | 0 | 964 字节 |
| 最终 `0.1.5-stack-fix` | 600.19 秒 | 133 | 0 | 964 字节 |

最终观察期内一次连接失败后自行恢复轮询，启动标识始终不变，栈保护值全程正常。
随后执行一次主动软件重启，启动原因是预期的 reason=4；31 秒后已完成 7 次新成功轮询，
配置、公钥就绪状态和任务高水位保留，没有再次复位。

固件编译通过，45 项协议检查、9 项签名包检查通过，其中签名包测试包括与框架官方
`signing.py` 的兼容性比较。USB 写入通过哈希校验。

这次观察支持本修复解决已复现的栈溢出/WDT 问题，不代表无限时长或所有网络条件的保证。
本修订的完整生产签名 HTTPS OTA 下载、验签提交和新版本心跳尚未实测；
`signed_ota_ready=true` 只表示公钥和升级接口已就绪。
